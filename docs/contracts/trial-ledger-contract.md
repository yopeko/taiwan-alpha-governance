# 試驗登錄契約

| 欄位 | 值 |
|---|---|
| 契約版本 | `trial-ledger-v1.0.0`（2026-08-28）|
| 狀態 | `baseline-approved`，2026-08-28 |
| 用途 | 記錄每一次在開發區上跑過的組態，以及它有沒有影響過任何選擇 |
| 核准 | Product Owner（單一簽核人）|

## 0. 這份契約是為了補一個不對稱

專案精心計數了一個目前是 0 的東西——[封存區開封](nested-validation-contract.md)有 append-only ledger、有守門測試、有三道拒絕。

而**真正在累積的那個完全沒有記錄**。

到 2026-08-28 為止，開發區與全窗口上至少跑過九次組態，其中四次是名額掃描（2／5／10／20，然後選了一個）。那是多重比較的教科書形狀，而它不在任何地方。

**九次未記錄的試驗，比一次記錄在案的開封更值得擔心。**

## 1. 什麼算一次試驗

**在研究資料上跑一次回測，就是一次試驗。** 不論它是探針、候選、敏感度還是隨手看看。

沒有例外，因為例外會變成分類的空間，而分類的空間會變成「這次不算」。

## 2. 但不是每次試驗都增加多重比較

**多重比較累積於一次結果影響了一個選擇。**

一次跑完、報告出來、沒有被拿來決定任何事的執行，不會讓後續結論變得比較不可信。一次跑完之後有人說「那就用十個名額」的執行，會。

因此每一列必填 `influenced_a_choice` 與 `choice_made`：

| `influenced_a_choice` | 意義 | 例 |
|---|---|---|
| `false` | 結果被呈報，未用於選擇 | 候選報告的兩個參與率——契約要求並列，不擇一 |
| `true` | 結果改變了後續的組態或決定 | 名額掃描 2／5／10／20，其後 D16 取 10 |

`true` 的那些構成**選擇預算**。`false` 的不構成，但仍必須登錄——因為「它有沒有影響選擇」是一個會被事後重新詮釋的判斷，而登錄的時點就是它的證據。

### 已宣告的敏感度軸不算選擇

參與率 0.01／0.001 由[對照比較契約](control-comparison-contract.md) §2.5 要求並列呈報，兩端都必須讀。**並列不是擇一**，所以它們是 `false`。

這個區分本身是判斷，所以它寫在契約裡而不是留給每次登錄者自己想。

## 3. 每列必填

| 欄位 | 說明 |
|---|---|
| `trial_number` | 流水號，1-based |
| `recorded_at` | 登錄時間 |
| `config` | 完整組態：排序函式、股票池、lookback、停損、持有上限、參與率、期初資金 |
| `dataset` | 資料集 id 與雜湊 |
| `code_commit` | 執行時的 git commit |
| `purpose` | `probe`／`candidate`／`sensitivity`／`parameter-search` |
| `influenced_a_choice` | 布林，見 §2 |
| `choice_made` | 若為真，寫下那個選擇是什麼 |
| `result_pointer` | 產物位置，或「未保存」 |
| `record_basis` | `contemporaneous` 或 `reconstructed` |

### `record_basis` 為什麼必填

2026-08-28 之前的九次是**事後由文件重建的**，不是當時記下的。兩者的可信度不同：重建會漏掉沒有留下文件的執行，而漏掉的那些正是最可能不利的那些。

**把它標出來，比讓它看起來像當時記錄誠實。**

## 4. 拒絕

登錄器在下列情況拒絕：

1. **工作樹不乾淨。** `code_commit` 要指認跑的是哪一份程式碼，髒工作樹讓它指不準——與巢狀驗證產生器同一條規則。
2. **同一組態重複登錄而未說明。** 重跑是正當的（修好 bug 之後就該重跑），但它必須說出為什麼，否則計數會把同一次試驗數成兩次，或把兩次數成一次。
3. **`influenced_a_choice` 為真而 `choice_made` 為空。** 說有影響卻說不出影響了什麼，等於沒說。

## 5. 這份契約不做的事

- **不設上限。** 與封存區同一個理由：任何上限都會變成「這次特殊」。它只讓數字被看見。
- **不做統計校正。** 它記錄選擇預算的大小，怎麼用那個數字是讀者的事。
- **不阻止任何試驗。** 它只確保試驗發生過這件事會留下來。
