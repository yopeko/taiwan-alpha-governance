# 巢狀驗證契約（M7）

| 欄位 | 值 |
|---|---|
| 契約版本 | `nested-validation-v1.0.0`（2026-08-28）|
| 狀態 | `baseline-approved`，2026-08-28 |
| 用途 | 定義封存樣本外的切法、開封的規則，以及 M7 產物的格式 |
| 核准 | Product Owner（單一簽核人）|

## 0. 這份契約要防的一件事

**同一批資料不能同時用來挑策略和證明策略。**

挑一個策略的過程就是在資料上做選擇。試過的每一個 lookback、每一個排序函式、每一次「這個窗口不太對，換一個」，都在把資料的形狀刻進候選裡。等到最後選出一個，它在那批資料上的表現已經不是預測，是回憶。

M6.3 已經示範過這件事的具體形狀：12-1 動能之所以能被稱為先驗，唯一的理由是它由沒看過這份資料的人在幾十年前定下。**那個性質很難再有第二次。** 之後的每一個候選都會多多少少誕生於這個窗口，所以需要一塊從來沒有參與過挑選的資料。

## 1. 切法：2025-01-01 為界

| | 場次 | 期間 | 佔比 |
|---|---:|---|---:|
| **開發區** | 1,458 | 2019-01-02 → 2024-12-31 | 79.2% |
| **封存區** | 382 | 2025-01-02 → 2026-08-03 | 20.8% |

### 為什麼是這條線

**按時間切，不隨機切。** 時間序列隨機切等於讓策略看到未來，這一條沒有討論空間。

**是曆年邊界，不是百分比。** 20%、25%、30% 都能講出理由，而能講出理由的數字就能被重講一次——每次重講都是一次微小的挑選。2025-01-01 是曆年，它不會因為結果不好看而被說成應該是 24% 或 26%。

**它剛好是既有的兩段歷史。** 開發區是 M6.1 六年回補新增的部分，封存區是原本的 M3 窗口。這不是設計出來的巧合，但它讓「這條線是不是被挑過」有一個獨立的答案：這條線在任何候選存在之前就存在了。

### 封存區只封「結果」，不封「歷史價格」

**候選可以讀 2025-01-01 之前的價格作為熱身，這不是洩漏。**

一個 252 場次的動能分數在 2025-01-02 那天需要 2024 年的價格，而 2024 年的價格在 2025-01-02 當天是已知事實。實盤交易者就是這樣算的。若禁止，封存區實際可評估的長度會少 252 場次——382 剩 130——而換來的不是更嚴謹，是更少的證據。

被封的是**結果**：2025-01-01 之後的任何報酬、回撤、成交或拒絕，都不得參與任何候選的挑選、調整或淘汰。

## 2. 封存是機制，不只是自律

**開發用的資料集實體上不含封存區的列。**

`split_sealed_dataset.py` 由完整資料集產生兩份：

```
<root>/development/    research_dataset.parquet   2019-01-02 → 2024-12-31
<root>/sealed/         research_dataset.parquet   2025-01-02 → 2026-08-03
```

開發區那份**另含封存區之前的完整價格歷史**（它本來就有），所以熱身不需要開封。

一份缺了那些列的資料集，無法產生那些列的結果。這比任何規定都可靠。

## 3. 開封規則

### 3.1 每次開封都要留下記錄

`sealed_evaluation_ledger.jsonl`，append-only，每次對封存區跑回測都必須追加一列：

| 欄位 | 說明 |
|---|---|
| `evaluated_at` | 時間 |
| `candidate_id` | 候選識別，含 `ranking_function`、`universe` 與全部參數 |
| `candidate_commit` | 該候選定案時的 git commit。**必須早於本次評估** |
| `development_report` | 該候選在開發區的報告位置與雜湊 |
| `sealed_report` | 本次封存區報告位置與雜湊 |
| `seal_opening_number` | 這是第幾次開封 |

**`candidate_commit` 早於評估時間，是先驗的唯一機械證據。** 與 M6.3 記下的同一條原則，而 M6.3 那次我沒有做到——先跑了才提交，只能靠自述。這份契約把它變成必填欄位。

### 3.2 開封次數是有限的，且數字要被看見

**沒有硬性上限，但每一份 M7 產物必須印出當前的開封總數。**

不設上限是因為任何上限都會被說成「這次特殊」。而印出次數的效果不同：第 12 次開封的報告上寫著 12，讀者自己會知道那個 p 值該打幾折。

**同一個候選重複開封，每次都算一次。** 「上次跑錯參數」也算。

### 3.2b 產生器的三道拒絕

`run_nested_validation.py` 在下列任一情況拒絕執行：

1. **未傳 `--i-am-spending-a-seal-opening`。** 這是減速丘不是保全措施，它存在的理由是讓開封永遠不會是在做別的事情時順手發生的。拒絕訊息會指向只跑開發區的便宜替代方案——因為一個不說明替代方案的拒絕會被繞過，而繞過的方式通常就是加上那個旗標。
2. **工作樹不乾淨。** `candidate_commit` 的用途是證明候選早於評估，而如果跑的程式碼不是那個 commit 裡的程式碼，這個證明沒有價值。
3. 產物寫入失敗時**不追加開封記錄**。一次沒有產出產物的執行沒有花掉開封，記上一次會高估成本，正如漏記會低估。

### 3.3 開封之後不得回頭修改候選

一個候選在封存區跑過之後，**它的任何參數變更都產生一個新候選**，而新候選的開發區工作必須重做。

不是為了懲罰，是因為改過的那個版本已經看過封存區了。

## 4. M7 產物

一個 parquet 加一份 manifest，與其餘 lane 相同：

```
<m7-root>/
    nested_validation.parquet     每個候選每個規模每個參與率一列
    validation_manifest.json      元資料、譜系、開封記錄摘要
```

### 4.1 每列必填

| 欄位 | 說明 |
|---|---|
| `candidate_id` / `ranking_function` / `universe` | 候選識別 |
| `segment` | `development` 或 `sealed` |
| `scale` | `m0-execution` 或 `reference-measurement` |
| `participation_rate` | 0.01 或 0.001 |
| `return_pct` / `drawdown_pct` / `completed_trades` | 該區段的表現 |
| `cost_share_of_turnover` | 成本佔成交額 |
| `selection_logic_measured` | 依候選報告契約 §3 |

**兩個區段都必須在場。** 只有封存區的報告看不出退化幅度，而退化幅度才是這份產物存在的理由。

### 4.2 manifest 必填

| 欄位 | 說明 |
|---|---|
| `seal_opening_number` | 這是第幾次開封 |
| `candidate_commit` / `evaluated_at` | 先驗證據 |
| `split_version` | 切法版本，變更切法即變更此值 |
| `development_dataset_sha256` / `sealed_dataset_sha256` | 兩份資料集的雜湊 |
| `degradation` | 每個規模的封存區減開發區報酬差 |

## 5. 什麼樣的結論可以被主張

### 可以

- 「此候選在封存區的表現為 X，該候選在此之前從未接觸該區段。」
- 「開發區到封存區的退化為 Y 個百分點。」

### 不可以

- **不能只報封存區。** 沒有開發區的數字就看不出退化，而一個在兩邊都平庸的候選與一個在開發區驚人、封存區崩潰的候選，只看封存區時可能長得一樣。
- **不能因為封存區表現不好就調整候選再跑一次。** 那正是 §3.3 禁止的，而且它會讓封存區在幾次之後變成第二個開發區。
- **不能主張統計顯著性。** 382 個場次的一次評估不提供它。
- **不能把 `m0-execution` 的報酬當作策略證據**（ADR-0002 決策 1）。

## 6. 這份契約承認的限制

**封存區只有一段，而且是最近的一段。** 2025-01 至 2026-08 是一個特定的市況，一個候選在它上面成功不代表在別的市況成功。真正的巢狀驗證會滾動多個外層折疊，而 1,840 個場次不夠切成多折還讓每折有足夠交易。

**這是一次留出法，不是巢狀交叉驗證。** 名字裡的「巢狀」指的是「挑選在內、驗證在外」這個結構，不是折疊數。寫在這裡，免得日後被讀成後者。

**2026-09-03：這一段與 M0 §9.1 的衝突已被承認並處理。** M0 要求 walk-forward folds，本節寫著辦不到，而兩份都是 `baseline-approved`——所以在此之前 M0 有一條要求從未被滿足也從未被豁免。[D25](../evidence/m3-owner-decision-d25-2026-09-03.md) 於 [M0 §9.1.1](../m0-project-contract.md) 加了豁免，門檻為**開發區 1,650 個場次**，並預先寫定解除後的四個參數（錨定擴張窗口、`gap/purge` 21 場、folds 只切開發區、每折至少 250 筆完成交易）。

**該豁免不會自己到期。** 開發區兩端固定於 2019-01-01 與 `SEAL_FROM` 前一日，因此永久是 1,458 個場次；解除它需要**往 2019 之前回補歷史**，還差 192 個場次。

**封存區會用完。** 每一次開封都消耗它一點，而它不會再生。到某個時點它會失去意義，屆時唯一的補充來源是**時間往前走**——2026-08-03 之後的新資料。這是 M9 shadow／paper 存在的理由之一。
