# 對照比較契約

| 欄位 | 值 |
|---|---|
| 契約版本 | `control-comparison-v1.1.0`（2026-08-27；§2.6 把可交易股票池由假設軸移入候選定義，假設軸改為參與率。Owner 決定選項丙）|
| 狀態 | `baseline-approved`，2026-08-27（Owner 決定，選項乙）|
| 用途 | 定義「這個改動有沒有幫助」要怎麼問才算數 |
| 核准 | Product Owner（單一簽核人）|

## 0. 為什麼需要它

M6.3 產出了第一個宣告排序函式的候選，於是第一次有人想問：**排序到底有沒有幫助？**

現在答不了。12-1 動能需要 252 場次熱身，排序版實質上到 2020-01-16 才開始交易，未排序探針從 2019-01-30 就在交易。兩邊走的不是同一段路，經歷的不是同一段市況。

而這個問題有一個特別的危險：**對照組怎麼設，必須在看到結果之前決定。** 看過結果再挑對照組，等於用結果挑對照組，而任何改動都能找到一段讓它好看的窗口。

所以這份契約先於任何比較存在，並且它自己不含任何結果。

## 1. 決定：只比共同窗口（Owner 選項乙）

**兩個候選各自照它自己的窗口跑完，比較只在兩者都在交易的那一段進行。**

共同窗口 = `[max(兩者首筆交易場次), min(兩者末筆交易場次)]`。

### 沒有選甲的那條路

選項甲是把兩邊都截成同一個窗口重跑，讓熱身較短的那個丟掉前面那段。乙不重跑，只在報告端限制比較區間。

**乙的代價要寫下來**：未排序版在共同窗口起點時已經交易了 249 個場次，帶著那段累積的 NAV 與未平倉部位進來。兩個帳戶在比較起點的狀態不同，而甲不會有這個問題。

因此乙的必填欄位（§2.3）要求揭露那個狀態，讓差異看得見而不是藏著。

## 2. 一份對照比較必須包含什麼

### 2.1 兩個候選各自的完整報告

比較不取代單獨的候選報告。兩份 [候選報告契約](candidate-report-contract.md) 產物都必須存在且可被指名，含各自的 `dataset_sha256` 與 `strategy_version`。

**兩份報告必須來自同一份資料集。** 不同的 `dataset_sha256` 不是對照，是兩件不相干的事。

### 2.2 共同窗口本身

| 欄位 | 說明 |
|---|---|
| `common_window_start` / `common_window_end` | 比較區間 |
| `window_source` | 起點與終點各自被誰決定（哪一個候選的哪一端）|
| `sessions_in_common_window` | 共同窗口的場次數 |
| `sessions_excluded_per_candidate` | 每個候選被排除在比較外的場次數 |

**`sessions_excluded_per_candidate` 是必填而非參考值。** 它是乙這條路的代價的大小，讀者要看得到。

### 2.3 每個候選在共同窗口起點的狀態

| 欄位 | 說明 |
|---|---|
| `nav_at_window_start` | 該點的 NAV。比較用的報酬以此為基準重算 |
| `open_positions_at_window_start` | 帶進比較區間的未平倉部位數 |
| `open_risk_at_window_start` | 帶進比較區間的總開放風險 |

一個帶著十檔部位進場的帳戶與一個空手進場的帳戶，在比較的第一天就不對等。**這三欄不是註腳，它們是乙與甲的差別。**

### 2.4 共同窗口內的指標

全部在共同窗口內重算，不得直接引用整段窗口的數字：

| 欄位 | 說明 |
|---|---|
| `return_pct_in_window` | 由 `nav_at_window_start` 到窗口末的報酬 |
| `drawdown_pct_in_window` | 在窗口內重新量測，不是整段的最大回撤 |
| `completed_trades_in_window` | 在窗口內完成的交易 |
| `cost_total_in_window` / `cost_share_of_turnover_in_window` | 窗口內的成本 |

**最大回撤特別容易出錯。** 整段窗口的最大回撤可能落在共同窗口之外，直接引用等於把一段沒有被比較的歷史算進比較。

### 2.5 兩個規模都要，兩個參與率都要

繼承既有的規則，理由相同——差距本身是資訊：

- **兩個規模**（ADR-0002 決策 3）：`m0-execution` 與 `reference-measurement`。
- **兩個參與率**：0.01 與 0.001。「一個帳戶可以假設吃下該場次成交量的多少」是假設不是量測，而一個會移動答案的假設應該放在軸上，不是釘成一個值。0.001 而非 0，因為零不是比較薄的市場，是關閉的市場。

因此一次完整的對照比較是 **2 候選 × 2 規模 × 2 參與率 = 8 列**。

### 2.6 可交易股票池屬於候選定義，不在假設軸上

**v1.1.0，2026-08-27**（Owner 決定，選項丙）。

`universe` 是每個候選的必填欄位，值為 `all` 或 `no-tpex-odd-lot-entry`。

v1.0.0 把它當成假設軸的一端（當時叫 `tpex-none`）。第一次實跑就顯示那是錯的分類：拒絕 TPEx 零股進場改變的是**持有哪些名字**，不是**拿得到多少**。同一個策略在兩個股票池下，參考規模報酬是 −3.57% 與 −37.76%——**那是兩本帳，不是一條誤差帶。**

判準：一個設定若改變候選能持有的證券集合，它屬於候選定義；若只改變同一集合中可成交的數量，它屬於假設軸。

要比較兩個股票池，就把它們當成兩個候選比較——那正是本契約的用途。

### 這條判準是二分法，而參與率不完全乾淨

要寫下來，免得被讀成參與率只動數量。

參與率降低時**沒有任何一筆進場被拒**（實測：0.01 與 0.001 兩次的流動性拒絕都是 0）。改變的是成交數量——委託變成部分成交。

但部分成交的比例不是均勻的：`可成交量 = 成交量 × 參與率`，而委託股數由風險政策決定且與成交量無關。所以參與率降低時，**薄的名字縮得比厚的名字多**，帳面的權重因此往流動性高的那一端傾斜。

**它仍在判準的「數量」那一側**（能持有的集合沒變），但它不是純粹的數量旋鈕。任何依賴參與率的結論都要連這句一起讀。

12-1 動能候選在參考規模的實測：參與率 0.01 報酬 −2.33%、1,204 筆；0.001 報酬 +45.35%、1,487 筆。交易筆數上升是因為部分成交把出場拆成更多腿。

## 3. 什麼樣的結論可以被主張

### 可以

- 「在共同窗口內、在指定的規模與假設下，A 的某項指標優於 B。」

### 不可以

- **不能主張整段窗口的優劣。** 比較沒有涵蓋整段。
- **不能在四種（規模 × 參與率）組合中挑對自己有利的那一種來下結論。** 四組必須全部呈報；若四組的方向不一致，那個不一致本身就是結論。
- **不能把 `m0-execution` 的報酬當作策略證據**（ADR-0002 決策 1，仍然拘束）。
- **不能用 `selection_logic_measured` 為偽的候選做排序比較**（候選報告契約 §3）。

## 4. 對照組必須在看結果之前決定

這份契約定義的是**格式**，不是某一次比較。任何一次具體比較還必須在跑之前寫下：

1. 比較的是哪兩個候選，以及它們的差異是什麼；
2. 預期哪個方向會贏，或明確寫下「沒有預期」；
3. 什麼結果會被算作「沒有幫助」。

**第 3 點最容易被略過，而略過它等於讓任何結果都能被說成成功。**

與 M6.3 的先驗排序同一條原則：證據是 git 的時間順序。比較計畫要先進 commit，比較才能跑。

## 5. 本契約不涵蓋

- 統計顯著性。單一窗口的一次比較不提供它，本契約也不假裝提供。
- 哪一個候選比較好。比較是輸入，不是判決。
- M7 巢狀驗證的方法。本契約定義的是候選之間的兩兩比較，不是樣本外驗證。
