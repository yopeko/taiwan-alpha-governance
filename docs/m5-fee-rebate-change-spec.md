## 1. 事實

券商的手續費優惠不是成交時打折，是**先收全額、次月退還**：

> 證券手續費折讓：當月先收取全額手續費，於次月 15 日退回至客戶交割帳戶，遇假日則提早。

實際數字為**成交時收 20 元，次月 15 日退 19 元**。

因此同一筆成交有兩個成本。以本專案基準情境（NAV 10,000、股價 50、停損距離 8%，`plan_position` 得 18 股／900 元）計：

| | 金額 | 佔部位 |
|---|---:|---:|
| 成交當下現金支出 | 42 元（手續費 20×2 ＋ 稅 2）| **4.67%** |
| 退款後經濟成本 | 4 元（手續費 1×2 ＋ 稅 2）| **0.44%** |
| 應收退款 | 38 元 | 4.22% |

**證交稅不在折讓範圍內**，它是法定稅負不是券商收費。

## 2. 現行實作為何不足

`Ledger._post_costs` 在成交時把單一個手續費金額扣出 `settled_cash`。無論填哪一個數字都會錯在某處：

| 填入 | 後果 |
|---|---|
| 淨額 1 元 | 現金與購買力**高估** 38 元／每筆來回。違反 **M0 §6 不變量 5**「未授權的待交割資金不得被當成購買力」——那 19 元在入帳前不是購買力。 |
| 實扣 20 元 | 損益與 NAV **低估**。**最大回撤被高估**。 |

依 Phase 3 實測交易率（382 場次 49 筆來回，約每月 2.69 筆），常態未收金額為 **102–154 元，即 NAV 的 1.02%–1.54%**。Phase 3 在 NT$10,000 報出的最大回撤為 10.91%——這個量級的持續性低估不是捨入誤差。

另有一條不變量會被違反：**不變量 4**「每筆費用及稅額可回溯至 order 或 fill」。退款是次月彙總一次入帳的**單筆**現金流，但它退的是當月數十筆成交。若記成一筆總額，回溯即斷。

## 3. 設計

原則：**應收退款計入 NAV，不計入購買力。** 這與帳本既有的 `unsettled_proceeds` 是同一種東西的第二個實例——已經確定會拿到、但還沒到手，因此可以計價值、不可以拿去買股票。

### 3.1 `BrokerTerms`

新增折讓子結構，同時表達實收與淨額。不以單一 `minimum_commission` 承載兩種語意。

```
commission_rate            0.001425   # 牌告，實收依據
minimum_commission         20         # 實收下限（現行欄位語意收斂為「實收」）
rebate_commission_rate     0.000285   # 淨額費率（2 折）
rebate_minimum_commission  1          # 淨額下限
rebate_payment_day         15         # 次月幾日
rebate_scope               "commission-only"
```

`rebate_*` 全部為 `None` 時，行為與現行完全相同——**沒有折讓的券商不需要改任何呼叫端**。

### 3.2 `CostBreakdown`

| 新欄位 | 意義 |
|---|---|
| `commission_charged` | 成交時實際扣的金額 |
| `commission_net` | 退款後的經濟成本 |
| `commission_rebate` | 兩者之差，即應收金額 |
| `rebate_due_on` | 應收到期日 |

現行 `commission` 欄位**收斂為 `commission_charged` 的別名**並標記 deprecated，不直接刪除——既有呼叫端在遷移完成前仍需可用，而靜默改變一個欄位的語意正是這份文件在處理的那類缺陷。

### 3.3 `Ledger`

新增與 `PendingItem` 平行的 `RebateReceivable`：

```
due_on     date
order_id   str
fill_id    str      # 逐筆掛帳，不變量 4 靠它成立
amount     Decimal
```

| 成員 | 變更 |
|---|---|
| `_post_costs` | 扣 `commission_charged`；若有折讓，同時掛一筆 `RebateReceivable` |
| `rebate_receivable`（新）| 未到期應收總額 |
| `nav()` | 加上 `+ self.rebate_receivable` |
| `buying_power` | **不變**。應收刻意排除——這就是不變量 5 |
| `credit_rebates_through(session)`（新）| 與 `settle_through` 平行：到期者轉入 `settled_cash`，並為**每一筆**追加 `CashEntry(kind="commission-rebate", fill_id=原成交)` |

`journal_is_balanced` 與 `every_entry_traces_to_a_fill` 不需修改即應繼續成立——若不成立，是設計錯了，不是測試錯了。

### 3.4 到期日與「遇假日則提早」

公告是**提早**不是延後，因此以當月 15 日建模是所有可能日期中**最晚**的一個，應收因而在帳上停留最久、購買力壓得最緊。**誤差方向偏保守，結構上不可能高估購買力**——與 D9 全額交割採 `announced_at = effective_from` 的理由相同。

精確日期需銀行營業日曆；M3 的交易日曆不等於銀行日曆，不可直接借用。在取得之前一律使用 15 日並標記 `conservative-bound`。

### 3.5 `plan_position`

**Owner 裁決 2026-08-25：兩處皆用實扣 20 元。**

| 用途 | 使用 | 理由 |
|---|---|---|
| `spendable`（可動用現金）| **實扣 20 元** | 成交當下真的要有這筆錢 |
| 成本 vs 風險守衛 | **實扣 20 元** | 對一個一萬元的帳戶，被綁住 45 天的現金才是真正的約束 |

本文件原先提案守衛用淨額，理由是它的既有註解（「這麼小的部位其成本可能超過它被定量的風險」）陳述的是經濟意義。Owner 選擇了另一邊。

結果是**更嚴格的拒絕**：以基準情境計，來回實扣 42 元對上風險預算 75 元——用淨額 4 元時遠低於門檻，用實扣時佔了 56%，更接近拒絕線。方向安全，且與 M0「當股數、價格、停損距離與成本無法同時滿足風險上限時，答案是不交易」一致：無法同時滿足的判斷應該用真正要付出的現金。

**測試 #7 因此改寫**：`spendable` 與守衛都必須反映實扣；若實作把任一處換成淨額，同一組輸入必須產生不同（較寬鬆）的股數，該測試即失敗。

## 4. 測試（已實作，18 條）

實作過程中 `journal_is_balanced` 抓到一個真的疏漏：它是**獨立重算**恆等式的，而我先把 `rebate_receivable` 加進 `nav()` 卻沒加進它，下一次執行就紅了。這正是它把加總重寫一遍而不呼叫 `nav()` 的理由——**只改一邊會是失敗，不是沉默**。理由已寫進該函式的 docstring。

另外三條測試最初是我自己寫錯：它們忽略了帳本的預設滑價（成交價 50 × 1.002，18 股多 1.8 元），已改為滑價 0 以隔離要測的行為。

| # | 測試 | 修改前應失敗的原因 |
|---|---|---|
| 1 | 成交後 NAV 只減少淨額，不減少實扣額 | 現行少計應收 |
| 2 | `buying_power` 反映實扣額，不含應收 | 若填淨額則高估 |
| 3 | 每筆退款 `CashEntry` 都帶得回原成交的 `fill_id` | 現行無退款分錄 |
| 4 | 到期日之前不得入帳 | 現行無到期概念 |
| 5 | 同一筆應收重複入帳被拒（不變量 6）| 現行無此路徑 |
| 6 | `journal_is_balanced` 在含應收時仍成立 | 恆等式缺一項 |
| 7 | `plan_position` 的 `spendable` 用實扣：兩者不同時股數必須不同 | 現行同一數字 |
| 8 | `rebate_*` 為 `None` 時行為與現行逐位元組相同 | 迴歸保護 |
| 9 | 折讓不適用於證交稅 | 稅是法定，不可被折讓吃掉 |

## 5. 不在本變更範圍

- **不改 M0 §7.2 的研究預設條款。** 那是研究基準，改它要另一份 Owner 決定書。本變更只讓模型**有能力**表達折讓。
- 不改任何既有回測結果。Phase 0 與 Phase 3 的數字在其自身條款下仍然正確。
- 不決定要用哪一家券商。

## 6. 證據狀態與到期

低收 1 元屬「2026 限時優惠」；牌告為 **20 元**。**一個建立在促銷上的成本模型帶著到期日。**

優惠結束當日，磨損由 0.44% 跳回 4.67%（十倍），應收歸零。實作必須讓這是一個**組態變更**而非改程式：`rebate_*` 設為 `None` 即回到牌告行為，測試 #8 守住這條路徑。

**來源已於 2026-08-25 補齊**（見 [D14／D15 決定書](evidence/m3-owner-decisions-d14-d15-2026-08-25.md)）：（發布者身分不公開），`(withheld) publisher fee-rate page`，擷取日 2026-08-25。證據狀態由「未具名文件」升為 `publisher-published-rate`——來源機構、端點與擷取日期齊備，但非簽署契約。

頁面另有兩處沉默：優惠**未載明截止日**，零股計費規則**未單獨載明**。

**兩處都在同一天由 Owner 補齊**（2026-08-25，見上引 D14／D15 決定書），而本節原文寫成兩處仍然開著。2026-08-27 更正：

| 項目 | Owner 答覆 | 證據狀態 |
|---|---|---|
| 優惠期間 | **僅 2026 年**，即 2026-12-31 到期 | `owner-supplied` |
| 盤中零股適用上市（櫃）費率與低收 | 是 | `owner-supplied` |
| 優惠低收 1 元適用盤中零股 | 是 | `owner-supplied` |
| 低收計收單位 | **每筆委託且成交，不彙總** | `owner-supplied` |
| 折讓適用盤中零股 | 是 | `owner-supplied` |
| 手續費尾數 | 無條件捨去 | `owner-supplied` |

第三項是較不利的那個答案，且已經在承重：分批出場會逐筆付最低收費，這正是 Phase 0 `consistent_returns` 拒絕率 39% 的成因。第六項確認 `_truncate_to_dollar` 用 `ROUND_DOWN` 是對的。

`owner-supplied` 弱於發布者自己載明。**M10 仍為 `blocked`**，缺的是簽署契約與零股**成交**證據，後者與計費是兩回事。

到期既然已知，就可以排定重算，而 2026-08-27 排了：條款由散文改為資料（`scripts/lib/broker_terms.py`），`tests/unit/test_broker_terms_provenance.py` 的 `test_the_promotion_has_not_expired_unnoticed` 在 2027-01-01 轉紅並在 docstring 裡寫明該做什麼。退場仍是組態變更（`rebate_*` 設為 `None`），測試 #8 守住那條路徑。

## 7. 尚未解決

- 銀行營業日曆來源未定（§3.4）。

### 2026-08-28 由 Owner 補齊的四項

原列於本節、當日取得答覆。證據狀態 `owner-supplied`——頁面對這四項沉默，答覆來自具名者於可記錄日期。

**核銷有逐筆明細可對。** 次月 15 日入帳的是一筆總額，銀行存摺對不出來，但券商電子對帳單（或大戶投 APP 歷史帳務）是**逐筆成交級別**，每筆載明成交日期、股數、價格、當下扣款手續費（牌告全額）、以及該筆的應退折讓。當月逐筆應退加總即等於銀行入帳的單筆總額。

這解掉了本規格最大的一個未知：**逐筆應收有對得上的來源**，不必靠推算。原本傾向的 fail-closed 處置（金額不符即中止並保留差異，不自動調平）維持不變，但現在它是一條有明細可查的規則，而不是一條無從查起的規則。

**100 萬上限是分級不是全月取消。** 額度以**曆月**計，涵蓋電子管道的台股現貨成交金額（買進 + 賣出，整張與零股合併累計）。超限後：100 萬以內維持 2 折（最低 1 元），**超出的部分**自動切回常態電子單折扣（公版約 3.8 折，依開戶專案而定）。

所以模型不該在超限時整月拒絕，而該分級計算。本專案目前兩個規模都碰不到這個上限（參考規模 15 萬、六年成交額約三千萬，月均約 38 萬），但這是「碰不到」不是「不存在」，記在此處。

**未到期應收不會失效。** 銷戶的前提是帳戶「無未完成之交易帳戶（含申購、成交未交割、折讓款等）」，因此若有次月尚未入帳的折讓款，分公司會要求等到折讓確實退回交割戶後才完成銷戶。

**優惠若由券商提前中止亦不溯及既往。** 中止日前已成交的交易，仍依約於次月退還折讓。

兩者合起來，`RebateReceivable` 計入 NAV 但不計入購買力的處理是對的：它是一筆會到的錢，只是還沒到。原本擔心的「會蒸發的資產」不成立。
