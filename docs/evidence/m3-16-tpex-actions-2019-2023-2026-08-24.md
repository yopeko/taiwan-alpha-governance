# M3.16 上櫃公司行動 2019–2023 回補（2026-08-24）

## 0. 為什麼需要這一條 lane

六年價格回補在 2026-08-22 完成，但 coverage ledger 的 `corporate_action` 是**逐市場**判定的：TWSE 走月度區間端點，TPEx 沒有任何區間式歷史端點，唯一的官方路徑是 MOPS 逐 symbol-year 查詢。既有 lane `m3_tpex_actions_2024-2026` 只涵蓋民國 113/114/115。

因此在這條 lane 之前，2019-01-01 至 2023-12-31 的**每一個上櫃場次都會是 `unknown`**，理由碼 `tpex-action-year-not-captured`。六年回補實際買到的會是「上市六年、上櫃兩年」。

fail-closed 有正常運作——問題不是它判錯，是它正確地判出我們沒有資料。

## 2. 股票池不是用今天的名單推的

MOPS 逐 symbol-year 查詢，所以回補之前必須先有清單，而**清單的來源決定了這次回補能不能看見已下市的證券**。

沿用 2024–2026 那份 899 檔（推導自 2025–2026 報價）等於拿今日名單問六年前。改由 [`derive_tpex_action_universe.py`](../../scripts/m3/derive_tpex_action_universe.py) 從 2019–2024 官方報價封存重放推導：862 檔、1,216 個場次（另 610 個零列休市日，合計 1,826 個日曆日，與窗口相符）。

比對舊清單：

| | 檔數 |
|---|---:|
| 在窗口內交易過、**不在**舊清單 | **55** |
| 在舊清單、窗口內未交易 | 92（2023 年後才上櫃，正確排除）|

那 55 檔的最後交易年為 2019/2020/2021/2022/2023 = 11/12/7/8/17，含 1795 美時、1752 南光、2233 宇隆等轉板案例。沿用舊清單，這 55 檔的公司行動一筆都問不到，且無 reason code。

**取數機制必須與它該捕捉的失敗模式無關。** 這與 M3 生命週期表由「有申報財報者」改為「公司存在」是同一條規則。

## 3. 開跑前修掉的缺陷：明細請求沒有重試

[`scripts/lib/retry_policy.py`](../../scripts/lib/retry_policy.py) 的 docstring 明寫它是為了什麼而存在：TPEx 擷取重試了 listing 卻沒重試逐筆明細，七個 MOPS 502 成了靜默缺口，而續跑以 listing 為鍵，重跑永遠不會回頭補。

**模組建好了，呼叫端沒有改。** 明細請求至今仍是零重試。一個所有請求種類「可以查詢」的物件，不等於一條所有請求種類「必須走」的路徑。

修正：新增 `request_with_retry()`（不吞例外，用盡後把原例外拋回給呼叫端記成證據），兩個呼叫端都改走它，`--retry-limit` 改為預設取 MOPS 政策自己的上限（5）而非把它壓到 3 的字面值。

[`tests/unit/test_capture_retry_coverage.py`](../../tests/unit/test_capture_retry_coverage.py) 九條：五條驗 helper 行為，四條以 AST 守住呼叫端（每個帶 `timeout` 的 HTTP 呼叫必須位於某個被 `request_with_retry` 包住的函式內）。修改前對 HEAD 實測為 0 個被包住的函式、2 個無防護 POST，兩條測試 FAIL。

**實測效益**：本次記錄 33 次失敗嘗試、28 個 period，其中

```
MOPS-TPEX-ACTIONS-LIST  /http-error-captured   18
MOPS-TPEX-ACTIONS-LIST  /transport-failed       3
MOPS-TPEX-ACTIONS-DETAIL/http-error-captured   12   <-- 修正前為零重試
```

28 個 period 全部重試後成功，永久缺口 0。**那 12 筆在修正之前會全部成為靜默的永久缺口。** 三年份 lane 是 2,697 個 symbol-year 出現 7 筆，等比例推估 4,310 約 11 筆，實測 12 筆。

## 4. 一條因果鏈，終點是 manifest 被抹掉

擷取本身完成得很乾淨，出問題的是它對自己的記述。

1. 既有 tw-sepa-screener 正式日更管線在 15:40–16:03 寫了自己的 store（當日行情、當月營收、股票主檔、DuckDB）。與本次擷取無關——擷取受 `require_daily_price_output_root` 限制只能寫 `C:\tmp` 底下。
2. `production_unchanged` 因此為 `False`。
3. 舊的結束邏輯是 `return 0 if production_unchanged and failures == 0 else 1`，於是**一次成功的擷取以 exit 1 結束**。
4. 監督腳本看到非零、60 秒後重啟。
5. attempt 2 跑 12 秒、全部 `already-captured`，然後用自己的空計數**覆寫了 manifest**：`total_announcements: 0`。

三個修正：

**守衛改為指名。** `protected_changed: [...]` 取代布林值——`False` 分不出「擷取寫了不該寫的地方」與「正式管線更新自己的 store」，而這兩者需要相反的處置。

**受保護 store 變動不再等於擷取失敗。** 它被大聲印出來並寫進 run record，但不再影響 exit code。任何跨過正式管線日更時點的長時間執行都會踩到它，而讓監督腳本去重啟一個其實已經成功的擷取，正是這條 lane 的 manifest 失去的原因。

**manifest 改為由 ledger 推導，而非由行程計數器。** `lane_summary()` 讀 append-only ledger，以每個 symbol-year 的**第一個真實結果**計數；`already-captured` 是後一次執行的陳述，不是 lane 的性質。任何執行——包括什麼都沒做的續跑——都得到同一組真實總數。每次執行自己的記錄另外附加到 `capture_runs.jsonl`，同樣 append-only。

另新增 `--rewrite-manifest`：不送任何請求，只從 ledger 重算 manifest。本 lane 的 manifest 即以此修復。

ledger 當初就是為了「覆寫等於抹掉這支腳本存在的理由」而設計成附加的。**同一條教訓沒有套用到第二個輸出上**，這次才發現。

## 5. 明細的鍵不是身分

`company:TPEX:{symbol}:announced:{date}` 在本 lane 有 **18 個 period 載著兩份不同 payload**，已封存的 2024–2026 lane 另有 9 個。

18 個全部是**不同的請求**（請求指紋 0 個相同），兩種形狀：

| 形狀 | 個數 |
|---|---:|
| 同 DATE1、異 SEQ_NO（同日兩則公告）| 11 |
| 異 DATE1、同 SEQ_NO（兩筆記錄解析到同一公告日）| 6 |
| 兩者皆異 | 1 |

只用 SEQ_NO 只能區分 12/18；`(DATE1, SEQ_NO)` 可區分 18/18。

**沒有位元組遺失**——儲存是內容定址的，兩份都在，明細觀測數 3,428 恰等於公告數。但這不只是標籤問題：下游 `build_prices_actions.py` 是**從這個字串取出公告日寫進 `announced_at`** 的，而 `announced_at` 決定 as-of 可見度。

修正：新鍵追加 `:src:{DATE1}-{SEQ_NO}`，`announced:` 段原封不動（下游取值語意不變），下游 regex 的後綴設為可選，因此**兩條已封存的 lane 仍可解析**。

已封存的兩條 lane 保留較粗的舊鍵。不回頭重抓：儲存是 append-only 的證據層，重抓只會把同樣的 payload 以新名字再存一份，比現況更糟。已知的模糊性記在此處，並由 [`tests/unit/test_tpex_action_lane_identity.py`](../../tests/unit/test_tpex_action_lane_identity.py) 十條測試盯著，其中三條直接用本 lane 的真實碰撞資料。

## 6. 一行 ledger 的落差，以及它為什麼不是資料落差

`symbol_years_captured` 4,309，`listing_observations` 4,310。差的是 `company:TPEX:3276:year:108`，觀測時間 `2026-08-23T16:32:52Z`——**正是機器進入睡眠、第一個行程中斷的瞬間**。

觀測已存入（`hash-verified`），ledger 那一行沒寫成。續跑以觀測為鍵，因此把它視為已完成，永遠不會補那一行。

離線重放該 blob 確認：**3276 在民國 108 年公告數為 0**，沒有明細需要抓，什麼都沒漏。正確的結果應是 `official-no-announcements`。

根因是寫入順序：**觀測先寫、ledger 後附加**，兩者之間被中斷就會留下沒有帳可查的資料。

處置是**呈報而非修補**。manifest 新增 `ledger_reconciled` 與 `symbol_years_without_ledger_outcome`，本 lane 誠實記為 `false` / `1`。位元組是證據；與位元組不符的計數是要給人看的問題，不是靠補一行假帳就能抹平的東西。

## 7. 這條 lane 完成不代表

- 六年窗口已可回測——staging 尚未以新窗口重建，coverage ledger v5 尚未執行。
- `m3_tpex_actions_2019-2023` 已進入 canonical 表——它目前只在 `build_staging.py` 的 `ARCHIVES` 中登記。
- 上櫃 2019–2023 已是 `supported`——那要等 v5 實際跑完並通過完整資料族檢查。
- 廠商依賴已解除——股票池、板別區間與全額交割仍由 TEJ 定義。
