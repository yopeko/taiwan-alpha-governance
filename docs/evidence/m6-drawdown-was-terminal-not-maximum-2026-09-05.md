# 「最大回撤」一直是期末回撤，而 M0 §8.1 的門檻就是一個回撤門檻（2026-09-05）

| 欄位 | 值 |
|---|---|
| 日期 | 2026-09-05 |
| 起因 | 重跑受影響產物時，動能在參考規模報出**回撤 0.00%** |
| 影響 | **本倉庫每一份候選報告的 `drawdown_pct`** |
| 修正 | `drawdown_pct` 改為權益曲線的最大回撤；期末值保留為 `terminal_drawdown_pct` |
| 重跑 | **不需要**——每份報告都帶 `equity`，修正是一次計算 |

## 0. 它長什麼樣

```python
# m5/ledger.py
def drawdown(self) -> Decimal:
    latest = self._nav_history[-1][1]
    return (self._high_water - latest) / self._high_water
```

`(高水位 − 最新) / 高水位`。**此刻的回撤。**

而驅動器：

```python
"drawdown_pct": float(ledger.drawdown) * 100,
...
print(f"最大回撤    {result['drawdown_pct']:.2f}%")
```

## 1. 為什麼沒有人發現

**兩者只有在執行結束於最低點時相等，而最常被看的那一份正好是那樣。**

| 執行 | 報告的「最大回撤」 | 權益曲線的最大回撤 |
|---|---:|---:|
| 動能 12-1 @ 10,000 | 65.93% | **65.93%** |
| **動能 12-1 @ 149,717** | **0.00%** | **59.27%** |
| 低波動 60 @ 149,717 | 8.21% | 9.97% |
| 週 MACD 篩選 @ 149,717 | 33.83% | 34.54% |
| 週 MACD 篩選（無持有上限）| 33.23% | 33.86% |

M0 規模的動能候選——被引用最多的那一份——結束在低點附近，所以**每一個看過
它的人都看到一個對的數字**。同一條策略在參考規模結束在歷史高點，於是報 0.00%。

### 2.1 而 D26 表格裡的 57.99% 是對的——這件事比 bug 本身更值得記

[D26](m3-owner-decision-d26-2026-09-04.md) 寫著動能回撤 57.99%，
而上表顯示那份報告的欄位是 **0.00%**、真值才是 57.99%。

因為**倉庫裡有兩支工具各自從權益曲線正確地算最大回撤**：

| 出處 | 算什麼 | 名字 |
|---|---|---|
| `run_ledger_backtest.py` | `ledger.drawdown`（期末）| **`drawdown_pct`** |
| `compare_candidates.py` | 權益曲線最大值 | `drawdown_pct_in_window` |
| `measure_halt_events.py` | 權益曲線最大值 | `max_drawdown_pct` |

而 `measure_halt_events.py` 把回測報告那個欄位命名為
**`final_drawdown_pct_from_run`**——**有人早就知道它是期末值**，在那裡命名
正確，而驅動器仍然把它印在「最大回撤」底下。

**所以這不是一個統一的 bug，是同一個名字有兩個定義，而拿到哪一個取決於是
哪支工具印的。** 那比統一的錯誤更難發現，也更難信任：既有證據文件裡的回撤
數字，正確與否要看它是從哪條路徑抄來的。

好消息是方向：走 `compare_candidates` 與 `measure_halt_events` 的結論
（比較 001、005，診斷 002）用的是對的數字；走回測報告欄位的（候選報告
parquet 的 `drawdown_pct`）用的是期末值。

## 3. 為什麼這件事重要

**M0 §8.1 的 8% 硬停止是一個回撤門檻。**

診斷 002、004 與候選 006 都是拿「回撤」去比 8%。其中診斷 002 的核心量測
（「82.2% 的場次處在高水位 −8% 之外」）**是另外從權益曲線算的，不受影響**；
但每一份報告表頭上的那個數字受影響。

方向是**一致地低估**：期末回撤永遠 ≤ 最大回撤。所以既有的「沒有通過 8%」
結論**只會更確定，不會翻轉**——一個報 33.83% 而實際 34.54% 的候選，兩個數字
都遠在 8% 之外。

**但一個報 0.00% 的候選看起來像通過了。** 那正是這個缺陷危險的地方，
而它已經在 2026-09-05 印出來過一次。

## 4. 修正

| 欄位 | 修正前 | 修正後 |
|---|---|---|
| `drawdown_pct` | `ledger.drawdown`（期末）| **權益曲線的最大回撤** |
| `terminal_drawdown_pct` | 不存在 | `ledger.drawdown`（期末）|

**期末回撤沒有被拿掉。** 它是一個關於真實帳戶的真實數字——「現在離高點多遠」
——它只是不叫最大回撤。拿掉它會讓一個既有欄位無聲消失。

**`m5/ledger.py` 沒有被修改。** 它是台股核心的逐位元鏡像，而 `ledger.drawdown`
本身沒有錯：它算的就是它說的東西。錯的是驅動器把它印在另一個標題下。

### 4.1 不需要重跑

每一份報告都帶 `equity`——完整的每日 NAV 序列。所以任何一份既有產物的真正
最大回撤，**由它自己的檔案就算得出來**，不必重跑。

這和 [2026-09-04 的停損成交價修正](m6-gapped-stop-fill-2026-09-04.md)不同：
那一次改的是成交，所有下游數字都變了，代價是重跑 42 個臂。這一次改的是
**一個從既有資料算出來的欄位**。

10 條測試，其中一條就是缺陷本身：`100 → 40 → 100` 的最大回撤是 60%，
期末回撤是 0%。

## 5. 這是同一天的第三個發現，而三個都出自同一個動作

1. **[持股清單](m6-weekly-macd-screen-2026-09-05.md) §2.5**：`open_at_end: 1` 展開後，
   是一個持有 983 個場次、其中 977 個場次沒有報價的部位
2. **同 §2.7**：放寬持有上限的預期被否證——放掉的部位大多變成停損不是停利
3. **本文件**：回撤一直是期末值

**三個都來自「把已經在報告裡的東西列出來」。** 沒有一個需要新的資料，
沒有一個需要新的量測方法。它們藏在聚合數字後面，而聚合數字沒有說謊——
它只是沒有被展開過。
