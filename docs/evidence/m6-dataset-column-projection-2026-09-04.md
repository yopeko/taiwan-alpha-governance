# 回測器的日線層：記憶體 7.56 → 1.35 GB，耗時 422 → 165 秒，輸出逐欄相同（2026-09-04）

| 欄位 | 值 |
|---|---|
| 日期 | 2026-09-04 |
| 起因 | Owner 指出「記憶體只有 32 GB 根本沒有辦法運行」 |
| 變更 | `scripts/m6/run_ledger_backtest.py`：欄位投影、`__slots__` 列物件、逐欄值共用 |
| 驗證 | 同一組態跑兩次，**逐欄比對 1,221 筆交易與 1,862 個權益點** |
| 試驗登錄 | `probe`，`influenced_a_choice = false` |

## 0. 一句話

**三個改動，全部在日線層：只讀用得到的 12 欄（資料集有 23 欄）、列物件由 dict 換成 `__slots__`、每個相異值只保留一個物件。**

Python 峰值 **7.56 → 1.35 GB（−82%）**，耗時 **422 → 165 秒（−61%）**，輸出除了 `built_at` 時戳以外**逐欄相同**。

## 1. 為什麼這件事要緊

這台機器有 31.2 GB 實體記憶體。載入一次日線資料集就要 7.5 GB，所以**一次只能跑一個回測**。

2026-09-03 有兩個背景工作同時跑，兩個都被砍掉，輸出全空、exit code 4，看起來像程式錯誤。**2026-09-04 我在同一台機器上又做了一次**——基準回測跑著的時候我開了第二個量測工作，可用記憶體掉到 **0.5 GB**。這次在它出事之前查了記憶體並停掉第二個，回到 9.0 GB。

**同一個錯犯兩次，而中間我還把第一次寫進了證據文件。** 那不是記性問題，是**這台機器的實際限制沒有被當成限制對待**。

## 2. 變更

```python
DATASET_COLUMNS = (
    "market", "symbol", "session_date",
    "open", "high", "low", "close", "volume",
    "session_state", "tradability_state",
    "limit_up", "limit_down",
)

table = pq.read_table(root / "research_dataset.parquet",
                      columns=list(DATASET_COLUMNS))
```

資料集有 23 欄，這 12 欄是驅動器實際讀的。

列物件則由 dict 換成 `__slots__`，並在載入時逐欄共用值：

```python
class Bar:
    __slots__ = DATASET_COLUMNS

for name in DATASET_COLUMNS:
    pool: dict = {}
    columns.append([None if v is None else pool.setdefault(v, v)
                    for v in table.column(name).to_pylist()])
```

一個 12 鍵的 dict 帶著一張雜湊表，而驅動器每一次存取用的都是作者寫程式時就知道的固定欄名——那張表從來沒有被用到。

22 個存取點由 `row["close"]` 改成 `row.close`。

## 3. 這兩個改動的失效模式，以及守著它們的測試

**漏掉一欄，它會以 `None` 抵達——而 `None` 與「倉庫本來就沒有這個值」長得一模一樣。**

少一個 `close` 會被讀成「那天沒有報價」，然後那檔證券被靜默跳過。回測照樣跑完、照樣產出報告、照樣通過所有既有測試。

**`__slots__` 把這個失效模式關掉了**：dict 的 `.get()` 對沒讀到的欄位回 `None`，而未填的 slot 拋 `AttributeError`。一條測試直接斷言這件事。

清單本身**不靠記性維護**。`tests/unit/test_dataset_columns.py` 掃描驅動器原始碼裡對列的存取，**與資料集真正的 schema 取交集**，斷言交集全在投影清單中。schema 從 [`build_research_dataset.py`](../../scripts/m6/build_research_dataset.py) 的 `pa.field(...)` 宣告讀出來，**不需要本機資料**，所以守在快車道。

另外兩條盯著掃描本身：

- **若正則什麼都沒抓到，上面那條會空洞地通過。** 一個空洞地通過的測試比沒有測試更糟。
- **任何以資料集欄位名做的下標存取都要被抓到**，不管前面的運算式是什麼——見 §6，這一條是事後補的。

## 4. 量測

| | 基準 | 投影 12 欄 | **+ slots 與值共用** | |
|---|---:|---:|---:|---|
| Python 峰值 | 7.56 GB | 3.85 GB | **1.35 GB** | **−82%** |
| 耗時 | 422.0 s | 249.4 s | **165.0 s** | **−61%** |
| 完成交易 | 1,221 | 1,221 | **1,221** | 相同 |
| 最終 NAV | 142,800.12 | 142,800.12 | **142,800.12** | 相同 |

速度變快是附帶效果：少解析 11 欄、少配置千萬個 Python 物件、少一層 dict 雜湊查找。

**最後一欄是對 2026-09-03 原始基準的比對**，所以它同時驗證了兩層改動。

### 列表示法的成本，以 40 萬列切片實測外推

| 做法 | 全表 | |
|---|---:|---|
| dict（原始）| 3.37 GB | — |
| dict + 共用字串 | 2.41 GB | −28% |
| dict + 共用字串與數字 | 1.91 GB | −43% |
| **`__slots__` + 共用** | **0.59 GB** | **−83%** |

相異值數是關鍵：`session_state` 在整個窗口只有 **1 個**、`market` **2 個**、`tradability_state` **4 個**。dict 版本抱著幾百萬份同樣的字串。浮點欄同樣重複——40 萬列裡只有約 **4,400 個**相異收盤價，因為價格走在檔位格上。

**共用是按值共用，不會改變行為**：Python 比較字串與數字比的是值，而 `is None` 仍然成立因為 `None` 是單例且從不進池。

`momentum-12-1`，參考衡量規模 149,717，參與率 0.01，`lookback=20`，`stop_pct=0.08`。

## 5. 我第一次的驗證方法是壞的

第一次比對我把**整份輸出做 sha256**，得到兩個不同的雜湊，然後在輸出裡印了「\*\*\* 不同 \*\*\*」。

**而輸出裡有 `built_at` 時戳。** 那個雜湊在任何兩次執行之間都會不同——**它證明不了相同，也證明不了不同**。

看到雜湊不同時，正確的第一個反應是「我的檢查壞了」，因為同一份輸出的**交易數與最終 NAV 都相同**——那個組合在真正的行為差異下幾乎不可能出現。

改成逐欄比對之後：

```
共 1 處差異
  /built_at
      before: 2026-09-03T17:09:17.181208+00:00
      after : 2026-09-03T17:19:47.013578+00:00
```

**1,221 筆交易、1,862 個權益點、全部 manifest 欄位，其餘完全相同。**

**這是本週第六次「量到的東西是真的，但它衡量的不是我以為的那件事」。** 前五次都是基準或參考點出錯；這一次是**驗證方法本身**——我拿一個包含時戳的雜湊當作等價性證明。

## 6. 第三次測試設計本身出錯

轉 `__slots__` 時漏了兩個站點：

```python
rows[(s.market, s.symbol)]["tradability_state"]
```

變數叫 `rows` 不是 `row`，所以**我的 grep 與我自己寫的守門測試有同一個盲點**——兩者都只認變數名。執行在四分鐘後炸掉：`TypeError: 'Bar' object is not subscriptable`。

**大聲失敗比靜默好，但在提交前抓到更好。** 守門已改成掃描**任何**以資料集欄位名做的下標存取，不管前面的運算式是什麼。任何這種存取，不是「該放 `Bar` 的地方放了 dict」，就是「輸出欄位剛好與資料集欄位同名」——後者現在是空集合，並被宣告成一個具名常數，將來真撞名時得寫在那裡，而不是讓掃描悄悄放寬。

**這是同一天第三次「測試的設計本身出問題」**：時戳雜湊當等價性證明、正則抓不到東西會空洞通過、掃描只認變數名。三次的共同點是**我檢查了被檢查的東西，沒檢查檢查本身**。
