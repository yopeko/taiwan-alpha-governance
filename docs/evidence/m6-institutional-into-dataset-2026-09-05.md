## 0. 兩個必須一起決定的東西

接進資料集不是加四欄那麼簡單。[法人軌道那份](m3-institutional-lane-2026-09-05.md) §6
列了兩件必須同時解決的事，因為分開做就是種下缺陷：

1. **PIT 時點怎麼強制。** 買賣超收盤後才公布，T 日排名只能 T+1 進場。
2. **譜系成本。** 加欄位會產生新資料集，而既有報告全部引用舊資料集的雜湊。

第一件的答案是**不強制，而是讓它不可能發生**。第二件的答案是**量，不是重跑**。

## 1. 落後一個場次不是策略要記得的規則

### 1.1 資料集裡沒有同場次的數字

四個欄位全部叫 `..._prior_session`：

| 欄位 | 內容 |
|---|---|
| `foreign_net_prior_session` | 外資及陸資（不含外資自營商），**T−1 公布的** |
| `investment_trust_net_prior_session` | 投信 |
| `dealer_net_prior_session` | 自營商合計 |
| `total_net_prior_session` | 三大法人合計 |

**同場次的數字不在資料集裡。** 一條策略照字面讀就已經是對的；一條想要同場次
數字的策略，在這裡拿不到。

「用 T 日的排名在 T 日開盤進場」這個錯誤，因此**不是被規則禁止，是不存在**。

只帶四個而不是全部八個度量：這是策略會排序的四個，而回測已經要讀 393 萬列，
每一欄都有價錢（§3）。`foreign_net` 兩個市場都排除外資自營商，所以跨市場可比
——TWSE 根本沒有「外資合計」那一欄，帶它等於帶一個只有一個市場有的欄位。

### 1.2 零和 null 是兩個不同的事實

| 情形 | 值 | 列數 | 佔比 |
|---|---:|---:|---:|
| 前一場次被列進報表 | 報表的數字 | 2,980,004 | 75.8% |
| 前一場次**有報價**但不在報表 | **0** | 384,907 | 9.8% |
| 前一場次**沒有報價** | **null** | 563,909 | 14.4% |

中間那一格的依據是[軌道那份 §4](m3-institutional-lane-2026-09-05.md) 量出來的：
沒有列的證券，成交量中位數比有列的低一個數量級，而 TWSE 缺席者裡量最大的三檔
收在 0.73、1.80、2.51 元。**沒有列的意思是那天沒有法人單。**

把中間和下面兩格合併，不是替一檔那天不存在的證券發明一個零，就是丟掉
「沒有法人碰過」這個唯一能被篩選的訊號。

### 1.3 驗證：全窗口逐列對回法人表

用**獨立於建置器重寫的**程式（不呼叫建置器的任何函式）：

```
場次 1,862   檢查 3,926,710 列
  值與『前一場次報表』不符 : 0
  標 null 但前一場次有報價 : 0
  標 0 但前一場次沒有報價  : 0
第一個場次 2019-01-02: 2,110 列，非 null 0
```

**差一格不會壞任何東西，只會讓下游變得漂亮。** 所以它被逐列驗過，而不是
靠讀程式碼相信。

## 2. 譜系成本被量掉了，而不是被重跑掉

### 2.1 dataset-11 就是 dataset-10 加四欄

逐欄比對 3,928,820 列：

```
dataset-10 22 欄   dataset-11 26 欄
  只在 11: 四個 _prior_session 欄
  只在 10: （無）

22 個共有欄位逐列完全相同
```

所以**既有的候選報告、對照、診斷全部仍然有效且可並排比較**，只有
`dataset_sha256` 指向不同的世代。這一次不需要像 2026-09-04 那樣重跑 42 個臂。

順帶驗掉一句一直只是宣稱的話：`current_build.py` 寫著「pit-prices-14 只多
`transactions` 一欄，其餘 22 欄逐列相同」。dataset-10 建自 prices-13、
dataset-11 建自 prices-14，這次比對**就是那句話的證據**。

### 2.2 回測層級也等價

同一組態各跑一次（`momentum-12-1`、`rank-only`、lookback 20、停損 8%、
參與率 0.01、開發側 1,458 場次）：

| | HEAD 驅動器 × split-02 | 新驅動器 × split-03 |
|---|---:|---:|
| 報酬 | −47.076386056% | −47.076386056% |
| 最大回撤 | 65.92702369665822% | 65.92702369665822% |
| 期末 NAV | 5292.3613944 | 5292.3613944 |
| 完成交易 | 135 | 135 |
| 已實現損益 | 973.3613944 | 973.3613944 |
| 排序違反（塞不下）| 8 | 8 |

**欄位總差異 3 個，全部是預期內的**：`built_at`、`dataset_root`、
`dataset_sha256`。

### 2.3 封存切分

`split-03` 由 dataset-11 重建，**與 split-02 同界線同場次數**：
開發 1,458 場次／3,076,380 列，封存 404 場次／852,440 列，界線 2025-01-01。

**開封次數維持 0。** 重建切分不是開封。

## 3. 四欄的價錢，實測

split-03 開發側 3,076,380 列：

| | 12 欄 | 16 欄 |
|---|---:|---:|
| 常駐 | 1.235 GB | **1.504 GB** |
| 峰值 | 1.55 GB | 1.93 GB |
| 載入 | 23.3s | 28.5s |

**+0.269 GB、+22% 載入時間。**

我在註解裡第一版寫的是「約省三分之一 GB」——那是估的。實測是 0.269 GB，
而且條件式載入連這個都省不滿，因為空的 slot 本身就要約 0.09 GB。

考慮過只在策略需要時才填那四個 slot。**沒有採用**：它換來一個有時候完整、
有時候不完整的 `Bar`，而「這次執行到底載了沒有」是任何產物都答不出來的問題。
那比投影原本要防的失敗更糟。

## 4. 過程中修掉的四個東西

### 4.1 情形被從數字反推

第一版把「是哪一種情形」讀回自數值：全 0 就算「沒有法人單」。**一檔確實被
列進報表、四個數字都是零的證券會被記錯格**，manifest 會低報涵蓋率。改成由
條件直接回傳情形。

### 4.2 schema 掃描看不見新欄位

`test_dataset_columns` 靠掃描建置器裡的引號欄名字面來讀 schema。第一版把四個
欄位寫成生成式，**於是守門看不到它們**——一個宣稱涵蓋而實際少涵蓋四欄的守門，
正是那份測試自己寫下來要防的東西。改成逐條寫出。

### 4.3 路徑守門對新軌道視而不見

`test_no_hardcoded_warehouse_paths` 的樣式寫的是 M3 的 `staging`／`pit` 與
M6 的 `dataset`。`INSTITUTIONAL` 是第五個具名的倉庫根，**落在規則之外**
——而 `tw-alpha-m7-split-NN` 與 `tw-alpha-m6-report-NN` 從建成起就一直在外面。

試過把樣式放寬成 `tw-alpha-m\d+-[a-z-]*\d+`，**放寬過頭**：它會掃到
`tw-alpha-m2-shadow-20260803` 這一類不可變的日期封存，那是產物不是輪替世代，
由當初產生它們的 M2 腳本具名是對的。

改成**從 `current_build.py` 自己讀出根名**。以後在那裡宣告一條軌道，守門會
自己跟上——那正是原本的樣式想達到而達不到的性質。

### 4.4 而修正 4.2 的註解又炸掉了另一條守門

我在註解裡寫下那個掃描用的正則樣式，於是掃描把註解裡的示範欄名當成一個真的
欄位，`name` 進了 schema 集合，driver 裡的 `result['strategy']['name']`
被判成違規。**同一個形狀往上一層。**

## 5. 這一步還沒做的

  裡還沒有 `investment-trust-net`、`foreign-net-streak` 這一類。那是下一步，
  而且**每一條都要登記試驗**（M0 §9、[試驗登錄契約](../contracts/trial-ledger-contract.md)）。

  所需的 192 個場次是同一件事。
- **只有四個度量。** 外資自營、自營自行、自營避險、外資合計仍只在
  [法人軌道](m3-institutional-lane-2026-09-05.md)的表裡，需要時再接。
