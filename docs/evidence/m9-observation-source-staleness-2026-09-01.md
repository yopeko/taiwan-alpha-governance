# M9：把擷取排程起來之前量到的事——它會每天寫一份空觀察，而計數照樣爬（2026-09-01）

| | |
|---|---|
| 觸發 | 準備替 `capture_observation.py` 登記每日排程 |
| 結果 | **沒有登記排程。** 改為讓該腳本拒絕 |
| 契約 | [Shadow 觀察契約](../contracts/shadow-observation-contract.md) §4 |
| 計數 | **0/60，不變** |

## 0. 本來要做的事

[M6.1 之後的登錄表](../milestone-register.md)寫著：管線 shadow 的計數只能由時間累積，而擷取端已於 2026-08-29 補上（`capture_observation.py`）。合理的下一步是把它登記成每日排程，讓時間開始替專案工作。

**登記之前先量了一次，然後就沒有登記。**

## 1. 量到的

現有排程 `tw-alpha-daily-status` 跑的是 `scripts/m3/daily_status_snapshot.cmd`，**不是** `capture_observation.py`。後者沒有任何排程——這部分符合預期。

不符合預期的是這個：

```
倉庫  C:\tmp\tw-alpha-m3-pit-prices-12\daily_prices_pit.parquet
列數      3,316,101
最早場次  2019-01-02
最晚場次  2026-08-03      ← 落後 29 天
今天      2026-09-01
今天的列數  0
```

`capture_observation.observe()` 的第一件事是 `[row for row in prices if row["session_date"] == session]`。**在 2026-09-01 執行，那個清單是空的。**

於是產出的觀察是：兩個市場都 `unobserved`、`universe` 空、`bars` 空。

## 2. 為什麼這比「沒排程」嚴重

`observe_session.py` 比對觀察與倉庫的 as-of 重建，量四項差異。**一份空觀察與一份空重建之間，差異是零。**

零差異會通過契約 §3 的檢查，`counts_towards_threshold` 因此為真，**那一天就被算進 60 裡**。

所以：若 2026-09-01 把它排上每日，計數會在 60 個開市日之後到達 **60/60**，而它一天都沒有觀察到任何東西。

那份腳本自己的 docstring 早就寫過這個形狀：

> 沒有它，登錄會填滿披著觀察外衣的重建，計數到達 60，而它什麼也沒量。

**它防的是「晚於場次日擷取」那扇門。這次是同一個房間的另一扇門：不是遲到的觀察，是空白的觀察。**

## 3. 處置：拒絕，而不是排程

`capture_observation.py` 現在多讀一個值 `latest_session_in_source`（來源表實際到哪一天），並在下列情況拒絕：

```
場次 > 來源表最晚場次   →  拒絕
```

拒絕訊息說明它會空、會照樣計數，以及該先做什麼（把倉庫重建到該日）。

### 空的兩個成因必須分開

一份 `today` 為空的觀察有兩種成因，輸出長得一模一樣：

| 成因 | 判準 | 是不是觀察 |
|---|---|---|
| 當天休市 | 場次 **≤** 來源最晚場次 | **是。** 觀察到「那天沒開」正是要點 |
| 來源沒到那天 | 場次 **>** 來源最晚場次 | **不是。** 沒有東西可觀察 |

**只拒絕後者。** 若連休市日一起拒絕，每個假日都會變成計數的缺口，而那會讓 60 這個數字慢慢失去意義。

三條測試盯著這個區分，且不依賴本機倉庫（用小型 parquet 假資料），所以 CI 上也會跑。

## 4. 這對 M9 的意義

**M9 的瓶頸不是「沒有排程」，是倉庫沒有每日重建。**

管線 shadow 的整個設計前提是：當天實際擷取到的狀態，與倉庫日後的 as-of 重建，兩者可以比對。而倉庫目前是一次性的 scratch 建置（`pit-prices-12`，2026-08-25 建，窗口止於 2026-08-03），沒有任何排程在推進它。

在那件事解決之前，替 `capture_observation.py` 登記排程**不會讓計數變得有意義，只會讓它變得有數字**。

### 需要 Owner 決定的

要讓 `0/60` 開始真的累積，需要一條每日把倉庫推進到當日的路徑。那是一個新的工作項目，不是一次排程登記，因此**不在本文件的處置範圍內**，記在這裡等裁決。

在此之前，M9 的計數維持 **0/60**，而它停在 0 的理由現在是被寫下來的，不是沒有人注意到。
