# 歷史來源回到哪一年：TWSE 2004、TPEx 2007（2026-09-03）

| 欄位 | 值 |
|---|---|
| 日期 | 2026-09-03 |
| 起因 | [D25](m3-owner-decision-d25-2026-09-03.md) 的豁免要靠回補歷史才能解除，而沒有人量過來源到不到得了 |
| 程式 | `scripts/m3/probe_history_reach.py` |
| 產物 | `C:\tmp\tw-alpha-m3-history-reach\probe-2026-09-03.json` |
| 請求 | **60 次**，6 秒間隔，未寫入任何倉庫 |

## 0. 為什麼問這個

[D25](m3-owner-decision-d25-2026-09-03.md) 為 M0 §9.1 的 walk-forward folds 加了豁免，門檻是開發區 1,650 個場次。開發區**兩端固定**（2019-01-01 與 `SEAL_FROM` 前一日），所以永久是 1,458 場——**時間往前走不會解除這張豁免，只有往 2019 之前回補會**。

而 M3 從 2019 開始，是因為那是被擷取的範圍，**不是因為來源到那裡為止**。哪一個才對，沒有人量過。

## 1. 結果

| 市場 | 最早有資料 | 15 年中 reachable |
|---|---|---|
| **TWSE** | **2004** | **15 / 15** |
| **TPEX** | **2007** | 11 / 15 |

TWSE 每一年、兩個日期全部回了資料，列數 712 → 1,059，隨上市家數逐年增長。

TPEx 的四個非 reachable：

| 年 | 判定 | 意思 |
|---|---|---|
| 2004–2006 | `no-data-on-either-probe` | 兩個日期都空。**可能是來源到不了，也可能是舊格式** |
| 2008 | `error` | 兩個日期都是傳輸錯誤——**這不是「沒有資料」的證據** |

2009 起 TPEx 全部有資料。

## 2. 對 D25 豁免的直接答案

| 回補到 | 增加場次 | 開發區 | 可支撐 |
|---|---:|---:|---|
| 2018 | ~243 | 1,701 | **k=2 ✅**（門檻 1,650）|
| 2015 年中 | ~850 | 2,308 | k=2 ✅、**k=3 差 31 場** |
| 2009 | ~2,430 | 3,888 | k=4 ✅ |

**回補一年就足以解除 k=2 的豁免。**

### 但乾淨的區段只有一段

[M4 契約 §1.2.1](../contracts/m4-market-rules-contract.md) 明文約束：**漲跌停實作不得套用於 2015 年中之前**，因為漲跌幅當時是 7% 而 `PRICE_LIMIT_RATE = Decimal("0.10")` 是一個沒有日期的常數。

所以**乾淨的回補區段是 2015 年中 → 2018 年底，約 850 個場次**。再往前需要先取得官方的制度變更生效日並在 M4 契約中明列，否則整段的漲跌停必須 fail closed。

**k=3 差的那 31 個場次，正好落在不能碰的那一側。** 那不是巧合——門檻與制度邊界剛好撞在一起。

## 3. 「可達」不等於「可解析」

**本探測回答的是「端點會不會回傳有列的回應」，不是「現有解析器能不能把它變成合格的 staging 列」。** 那是兩個不同的宣稱，而證據就在資料裡。

TPEx 的列數不連續：

```
575, 611, 625, 638, 644, 663, 673, 685, 696, 718, 724, 733, 742, 766, 787
                                                  ↑ 2009–2018，隨家數增長，形狀合理
1003, 1118, 1445    ← 2007、2009-10、2010-03
```

TPEx 當年上市櫃約五、六百家。**1,445 與 1,118 不可能是家數**——那是舊年份的回應結構不同，而 `row_count` 取了最寬的表。

所以誠實的結論分三層：

| | |
|---|---|
| TWSE 回補到 2015 年中 | **可達，格式看起來一致** |
| TPEx 回補到 2018 | **可達** |
| TPEx 回補到 2010 之前 | **端點會回應，但格式未經驗證，現有解析器可能讀不了** |

驗證只有一條路：拿一天的舊 TPEx 回應實際跑一次現有解析器，看它產出幾列、欄位對不對。**那還沒做。**

## 4. 設計上刻意的兩件事

**每年兩個日期。** 一個日期分不出「來源到不了那一年」與「那天是假日」。三月與十月的第三個週三，**寫死在程式裡而不是每年挑**——挑日期若發生在看到哪些日期有回應之後，那就是選樣本。

**`unrecognised-shape` 不算空。** 一個解析器看不懂的回應是**關於解析器的事實**，不是關於來源的。把它記成「那年沒有資料」，會得出「來源到不了 2010」而真相是不會讀那個格式。

## 5. 一道沒有生效的護欄

探測程式帶了一道「輸出不得寫進倉庫」的檢查。**第一次執行時它把 `probe.json` 寫進了倉庫，而檢查什麼都沒說。**

```python
args.out.is_relative_to(REPO)     # args.out 是 "./probe.json"
# Path("probe.json").is_relative_to("C:/...") → False
```

相對路徑對絕對路徑永遠回 False。**護欄擋住的是我原本就不會犯的錯（傳絕對路徑進倉庫），漏掉的是我實際犯的那個。**

已修（先 `resolve()`），重驗會拒，殘留檔案已刪。**一道不會觸發的護欄比沒有護欄更糟，因為它被當成涵蓋。**

## 6. 還沒量的

**市場狀態（處置、注意、全額交割）與公司行動（除權息、減資、面額）能回到哪一年，沒有量過。**

這是真正的關卡：若那些端點回不到 2018 之前，回補來的年份會整片是 `unknown`——倉庫會誠實地說「不知道那天那檔能不能買」，而那樣的年份不能用來回測。

**價格可達不等於那些年可用。**

生命週期沒有這個問題：TEJ 主檔回到 **1962 年**（2,069 檔證券最早上市日 1962-02-09）。
