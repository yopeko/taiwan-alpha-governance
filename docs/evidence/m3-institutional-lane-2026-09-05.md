## 2. TPEx 的欄位順序不是假設出來的

TPEx 把七組欄位取了**同樣的三個名字**（買進股數／賣出股數／買賣超股數），
而 JSON 把說明哪組是哪組的表頭壓平了。**欄名完全不帶資訊。**

順序是用三條算術恆等式釘出來的：

```
g0 + g1 == g2        外資（不含自營）+ 外資自營 = 外資合計
g4 + g5 == g6        自營自行 + 自營避險 = 自營合計
g2 + g3 + g6 == T    三個小計 = 公布總計
```

推導用 2022-03-16，**確認用 2022-03-14 與 03-15**——形成假說的資料不能同時
當它的證據。兩個競爭順序在 741 列中分別壞掉 690 與 689 列。

**而這次建置是它們第一次面對全窗口。** 三條在 1,862 個場次上全部成立，
任何一條斷掉建置就會中止。TWSE 的兩條同樣如此（自營小計逐列、總計限四位數
普通股——權證上發行券商是外資自營商，同一筆進兩欄而公布總計只算一次）。

## 3. 找到並修掉一個會永久留洞的缺陷

### 3.1 它長什麼樣

TPEx 對 2025-04-09 的合法請求回了：

```json
{"stat":"ok","date":"114/04/09","tables":[{...,"data":[]}]}
```

641 位元組、**合法 JSON、日期正確、表是空的**。

那天 TPEx 有 **846 檔有量成交**。重問交易所，回 **887 列**。

### 3.2 為什麼所有守門都放行

| 層 | 判斷 | 結果 |
|---|---|---|
| 擷取儲存 | 位元組與雜湊相符 | `hash-verified`、`official-captured` |
| 守門 `payload_is_json` | 開頭是不是 `{` | **是** → 放行 |
| 續跑 `already_held` | 有沒有 hash-verified 且是 JSON | **有** → 永遠跳過 |
| 建置 | 有沒有列 | 沒有 → 記為 `no_rows`，與假日同一格 |

**這是我在 2026-09-04 為「HTTP 200 夾 HTML 錯誤頁」建的守門，淺了一格。**
那次擋住了，因為 HTML 不以 `{` 開頭。這一次穿過去了，而且撐完了整個
六年執行。

### 3.3 它是怎麼被抓到的

**不是被任何守門抓到的。是被算術抓到的。**

```
2,002 個平日 − 1,862 個場次 = 140 個非交易日
140 × 2 個市場 = 280
建置回報 no_rows = 281
差額 = 1
```

差額只有一個，那一個就是它。同時 `layouts_seen` 顯示 TPEX 1,861 而
TWSE 1,862——兩個獨立的數字指向同一天。

**而手算不會每次都做。**

### 3.4 兩層修正

| 層 | 修正 |
|---|---|
| 擷取守門 | `payload_is_json` → **`payload_has_rows`**。空表不算持有。代價：真正的非交易日每次續跑重問一次（280 次 × 6 秒 ≈ 28 分鐘），**這個代價寫在原始碼裡**，因為沒有標價的守門下次會被嫌慢拆掉 |
| 建置交叉檢查 | 新增 `verify_against_prices`：**價格倉庫裡有成交量的每一個市場場次，都必須有法人列**，否則建置中止 |

第二層是關鍵的那層。擷取端只知道自己拿到什麼，**不知道那天該不該有東西**；
只有倉庫知道哪幾天有交易。修正後：

```
traded_market_sessions      3,724
covered_market_sessions     3,724
covered_without_trading         0
```

## 4. 缺席不是缺資料，而誤用不會報錯

### 4.1 兩個交易所都不列出全部證券

兩邊都會發布 `total_net = 0` 的列（2–8%），所以報表不是「只列有動的」。
可是有量普通股的涵蓋率只有 **TWSE 0.97、TPEx 0.83**（中位場次）。

缺席的是誰？

| 場次 | 在席者量中位 | 缺席者量中位 |
|---|---:|---:|
| 2019-01-22 TPEx | 224,000 | **20,000** |
| 2019-11-01 TWSE | 504,994 | **29,000** |

TWSE 那批缺席者裡量最大的三檔，收盤價是 **0.73、1.80、2.51 元**。

**所以沒有列的意思是那天沒有法人單，不是資料缺。**

### 4.2 而缺席率隨年份收斂——這才是危險的部分

有量普通股當中，當天沒有法人列的比例：

| 年 | TWSE | TPEx |
|---:|---:|---:|
| 2019 | 10.6% | **36.6%** |
| 2020 | 4.7% | 31.4% |
| 2021 | 3.5% | 21.3% |
| 2022 | 3.3% | 18.3% |
| 2023 | 3.0% | 15.7% |
| 2024 | 1.5% | 9.0% |
| 2025 | 2.2% | 12.0% |
| 2026 | 1.0% | **9.2%** |

用 inner join 接這張表，會丟掉一批**隨年份變化、且與規模相關**的股票——
早年丟得多、小型股丟得多。那個偏誤朝著美化的方向（留下的都是大的、
法人碰過的），**而且不會有任何錯誤訊息**。

**正確用法：從可交易池 left join，買賣超填 0。**

寫在三個地方：模組 docstring、`dataset_manifest.json` 的 `notes`、
以及一條會失敗的測試。

## 5. 兩個市場沒有被對齊成同一個形狀

TPEx 自己的副標寫著其數字含 **普通股、鉅額、零股、綜合帳戶**；而 TPEx 的
**價格**表排除零股與盤後（[PIT 契約 §6.4.1](../contracts/pit-warehouse-contract.md)）。

所以同一個市場裡，法人成交量與交易成交量畫在不同範圍上。**記在列上
（`scope_note`），不是調和掉。**

## 6. 這條軌道還沒有做的事

- **沒有接進研究資料集。** dataset-10 沒有這些欄位，回測器讀不到它。
- **沒有登記任何試驗。** 一條用得到它的策略還不存在。
- **沒有處理 PIT 時點。** 買賣超收盤後才公布，所以 T 日的排名只能在 T+1
  進場。這寫在 manifest 的 `notes` 裡，**但沒有任何程式強制它**——
  接進資料集時必須連同這條一起做，否則它是一個前視缺陷的入口。
- **沒有回填 2019 之前。** TWSE 答得到 2012，TPEx 未測。窗口起點的決定
  （[歷史深度探測](m3-history-reach-probe-2026-09-03.md)）仍未定。
