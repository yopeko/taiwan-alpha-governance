| | |
|---|---|
| 觸發 | 為了讓 M9 計數開始累積，準備建立倉庫每日重建 |
| 結果 | **沒有建立每日重建。** 量出來它既不可行、也不是問題所在 |
| 契約 | [Shadow 觀察契約](../contracts/shadow-observation-contract.md) |
| 狀態 | **待 Owner 裁決**。M9 計數維持 `0/60` |
| 相關 | 同日稍早的[來源落後](m9-observation-source-staleness-2026-09-01.md)是同一件事的第一層 |

## 0. 本來要做的事，以及為什麼停下來

同日稍早發現 `capture_observation.py` 會寫出空觀察，處置是加拒絕條件。那份文件的結論是：**真正的瓶頸是倉庫沒有每日重建。**

於是下一步應該是建立每日重建。**量了兩件事之後沒有建。**

## 1. 每日全量重建不可行

[M3.17](m3-17-six-year-rebuild-2026-08-25.md) §記錄的實測：六年窗口的 `build_staging` 跑了 **79.8 分鐘**（且中途被系統睡眠殺過一次，之後才加上 `ES_SYSTEM_REQUIRED`）。canonical 表的建置另計。

每天跑一次 80 分鐘以上、且每個 generation 都要保留（`current_build.py`：「Generations are additive. An old root is left on disk so an old report can be re-read」），磁碟成長沒有上限。

**這條路不用再評估了。**

## 2. 但那不是真正的問題。兩邊在讀同一份表

```
capture_observation.observe(session, prices_root=PRICES, ...)
observe_session.reconstruct_snapshot() → default_warehouse() → Warehouse(CALENDAR, PRICES, STATUS)
```

`PRICES` 是同一個常數，指向同一個 `pit-prices-12`。

**觀察端與重建端讀的是同一份表。**

契約 §1 定義的是：

| | 何時取得 | 內容 |
|---|---|---|
| 當日觀察 | 交易日 D 收盤後 | **當天實際擷取到的**市場狀態 |
| as-of 重建 | 任何日後時點 | 倉庫回答「D 當天可知」的重建結果 |

「當天實際擷取到的」——**當前實作讀的不是擷取，是倉庫。**

### 這使差異的來源只剩一個

觀察是當日凍結成 JSON 的，所以它確實保留了 D 當天倉庫的樣子。若倉庫在 D 與比對之間被重建過並吸收了遲到資料，差異就會出現——機制不是完全不動。

**但差異只可能來自「倉庫被重建了」，不可能來自「當天實際看到的與倉庫說的不一樣」。** 而後者正是契約 §1 說整份文件要量的東西：

> 那句話目前由建構方式保證……**但它從來沒有被對照過當天實際看得到什麼。**

**現在它仍然沒有。** 對照的是倉庫的今天與倉庫的日後，不是市場的當天與倉庫的日後。

### 而在目前的靜態狀態下，差異結構性為零

倉庫最後一次建置是 2026-08-25，之後沒有排程在推進它。若現在開始觀察並在數週後比對，兩邊讀的是同一份未曾改變的表——**四項差異全部會是零。**

`counts_towards_threshold` 因此為真，計數會爬到 60/60，而報告會顯示**零差異**——契約 §1 稱之為「這個倉庫最強的一次驗證」。

**它會是一次拿表跟自己比得到的最強驗證。**

## 3. 處置：沒有實作，因為選哪一條會改變 60 天在量什麼

### 甲：每日全量重建倉庫

已由 §1 排除。80 分鐘以上、磁碟無上限。

### 乙：觀察端改為獨立的當日擷取（建議）

`capture_window.py` 已經能做這件事——直接向 TWSE／TPEx 抓指定日期的官方收盤表，可續跑、寫入隔離 root、保留非交易日回應作為證據。`--start` 與 `--end` 都設為當日即可。

每日鏈路：

```
capture_window.py  --start D --end D --output-root <當日 raw>
build_staging.py   <當日 raw>   → 小型 staging
build_prices_actions.py         → 當日 parquet
capture_observation.py --prices-root <當日 parquet>
```

依 M3.17 的實測，staging 六年 1,840 場次花 79.8 分鐘，**單日約數秒**。擷取受 6 秒禮貌間隔限制（[D 決定](m3-owner-decisions-and-capture-feasibility-2026-08-16.md)），單日兩個市場是分鐘級。

**這才讓兩邊成為兩個來源**，契約 §1 的主張因此第一次真的被對照。

代價要寫下來：多一條每日鏈路要維護，且擷取失敗會使當日不計入（契約 §4 已規定「擷取失敗不計」）。

### 丙：承認管線 shadow 目前量不到它宣稱要量的東西，暫緩計數

不實作任何東西，把 M9 的 `0/60` 標為 `blocked` 而非 `pending`，並寫明理由。

**這條的優點是誠實，缺點是時間繼續不替專案工作**——而[契約 §0](../contracts/shadow-observation-contract.md) 存在的全部理由就是「把時間變成證據」。

## 4. 建議

**選乙。** 理由是它同時解決兩層問題：來源落後（第一層）與兩邊同源（第二層），而成本是分鐘級而非小時級。

**但這是 Owner 的決定，不是我的**，因為它改變「一次觀察」的定義，而那是契約 §1 的內容。在裁決之前不實作，也不登記任何排程。

## 5. 這次沒有重蹈的那個錯

同日稍早的[來源落後文件](m9-observation-source-staleness-2026-09-01.md) §4 寫著「真正的瓶頸是倉庫沒有每日重建」。

**那句話是對的，但它把結論停在第一層。** 若照它直接去建每日重建，會花掉數十小時建一條 80 分鐘的每日鏈路，然後得到一個仍然在拿表跟自己比的比較。

先量再建，這次量到的東西推翻了幾小時前自己寫下的下一步。
